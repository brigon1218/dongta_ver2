## 1. Design Goals

1. **User-Centric Data Aggregation**: 여러 앱에 분산된 사용자의 활동 데이터를 한곳으로 집약
2. **Secure Account Management**: 비밀번호 변경 시 현재 비밀번호 검증 절차를 필수로 두어 보안 강화
3. **Integrated Financial View**: 충전(PaymentHistory)과 사용 내역을 하나의 타임라인으로 결합하여 제공
4. **Soft Account Deletion**: 데이터 무결성을 위해 즉시 삭제가 아닌 `is_active=False` 및 탈퇴 정보 기록 방식 채택

## 2. API Specification

### 2.1 프로필 및 계정 관리

| Method | Path | Description | Note |
|--------|------|-------------|------|
| GET | `/api/v1/mypage/profile/` | 내 상세 프로필 조회 | |
| PATCH | `/api/v1/mypage/profile/` | 내 기본 정보 수정 | 연락처, 주소 등 |
| POST | `/api/v1/mypage/password/` | 비밀번호 변경 | 현재 비밀번호 확인 필수 |

| Method | Path | Description | Note |
|--------|------|-------------|------|

| GET | `/api/v1/mypage/summary/` | 내 활동 요약 (대시보드) | 공고, 게시글, 업체 수 |

## 3. Core Logic Design

### 3.1 통합 포인트 내역 조회
- **Source**: `payment.PaymentHistory` (충전) 및 별도의 포인트 사용 기록(필요 시 모델 추가 검토)
- **Logic**: 
  - 현재 시스템에서는 `PaymentHistory`가 주된 기록임.
  - 사용 내역의 경우 `PointAccount.total_used` 업데이트 시 로그를 남기는 구조가 필요함. (추후 `PointLog` 모델 추가 설계 고려)
  - 초기 버전은 `PaymentHistory` 목록을 최신순으로 제공.

### 3.2 활동 요약 집계 (Activity Summary)
- 각 모듈의 모델을 카운트하여 반환:
  ```json
  {
    "counts": {
      "posts": 5,
      "comments": 12,
      "businesses": 1,
      "job_notices": 2
    }
  }
  ```
- 성능을 위해 `annotate` 또는 개별 `count()` 쿼리 수행.

### 3.3 회원 탈퇴 로직
1. 입력된 비밀번호 검증
2. `Member.is_active = False` 처리
3. `BaseModel`의 `soft_delete()` 호출
4. 탈퇴 일시 및 사유 저장

## 4. Component Structure

### 4.1 Serializers
- `UserProfileSerializer`: `accounts.Member` 모델 기반 필드 구성
- `PasswordChangeSerializer`: `old_password`, `new_password` 필드 및 검증 로직
- `ActivitySummarySerializer`: 집계된 카운트 정보를 담는 Simple Serializer

### 4.2 Views
- `ProfileView`: `RetrieveUpdateAPIView` 상속
- `ActivitySummaryView`: `APIView` 상속 및 커스텀 로직

---

## 5. Implementation Order

1. **Step 1**: `accounts` 앱 내의 정보를 활용한 기본 프로필 API 구현
2. **Step 2**: 비밀번호 변경 및 탈퇴 처리 로직 구현
3. **Step 3**: 각 앱별 활동 데이터 카운트 집계 API 구현
4. **Step 4**: 포인트 내역 통합 조회 로직 (Serializer 고도화)
5. **Step 5**: 마이페이지 전체 통합 테스트
