### 4.2 Phase 2-2: Data Synchronization (Score: 96%)

#### Celery Architecture

| Component | File | Description |
|-----------|------|-------------|
| Celery app | `dongta-django/config/celery.py` | 3 queues, task routes, beat schedule |
| Docker services | `dongta-django/docker-compose.yml` | celery-sync(x2), celery-payment(x1), celery-beat |

**Queue Configuration:**

| Queue | Workers | Purpose |
|-------|---------|---------|
| sync | 2 replicas | 회원/업체 데이터 동기화 |
| payment | 1 replica | 결제 데이터 동기화 |
| default | shared | 기타 비동기 작업 |

**Beat Schedule:**

| Schedule | Interval | Task |
|----------|----------|------|
| poll-pending-events | 5분 | PENDING EventOutbox 일괄 발행 |
| verify-sync-integrity | 매시간 | 정합성 검증 (DLQ/stale 감지) |
| clean-old-event-logs | 매일 02:00 | 7일 이상 완료 이벤트 정리 |

#### Sync App (`dongta-django/apps/sync/`)

| File | Description |
|------|-------------|
| models.py | EventOutbox (5-state 상태머신), SyncLog (모니터링 이력) |
| tasks.py | process_event_outbox, poll_pending_events, verify_sync_integrity, clean_old_event_logs |
| views.py | SyncStatusView, EventOutboxListView, EventOutboxRetryView, SyncLogListView |
| serializers.py | EventOutboxSerializer, SyncLogSerializer, SyncStatusSerializer |
| urls.py | /api/v1/sync/ (status, events, retry, logs) |
| management/commands/verify_sync.py | CLI 기반 동기화 검증 (--fix-stale, --report-only) |

**Data Flow:**

```
MySQL Trigger (tg_member_update/insert, tg_payment_insert)
    -> TBL_EVENT_OUTBOX (status=pending)
    -> Celery Beat: poll_pending_events (5분마다)
    -> process_event_outbox (개별 처리)
        -> _process_member_event() or _process_payment_event()
        -> PostgreSQL update_or_create
    -> outbox.mark_done()

실패 시: mark_failed() -> retry (지수 백오프) -> max_retries 초과 시 DLQ
```

## 9. Lessons Learned

### 9.1 What Worked Well

1. **Outbox Pattern**: MySQL 트리거 + Celery 폴링 조합이 안정적인 비동기 동기화 제공
2. **5-state 상태머신**: Design의 단순 boolean 대비 운영 관리 용이성 크게 향상
3. **모니터링 API**: Design에 없었으나 추가한 REST API 4종이 운영 가시성 확보
4. **Docker Compose**: YAML anchor + healthcheck 패턴으로 서비스 안정성 확보
5. **PDCA 프로세스**: 49% -> 93% 달성 과정에서 체계적 Gap 분석이 효과적

### 9.2 What Could Be Improved

1. **초기 분석 정확도**: v1.1 분석에서 구현된 기능을 미구현으로 오기재 (+5% 오차)
2. **Phase 2-3 분리**: 결제 시스템(Danal)을 별도 Phase로 분리해야 했음
3. **Monitoring 후순위**: Prometheus/Grafana를 Backlog로 미룬 것은 적절하나, 최소한의 알림(Slack)은 함께 구현했어야 함
