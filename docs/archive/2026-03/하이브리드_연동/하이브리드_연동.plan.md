## 1. Overview

### 1.1 Purpose

Phase 1에서 구축한 Django REST API를 PHP 레거시와 병행 운영하기 위해:

1. **Nginx 리버스 프록시**: 클라이언트 요청을 `/api/*` (Django) 또는 `/` (PHP)로 라우팅
2. **데이터 동기화**: MySQL (PHP) ↔ PostgreSQL (Django) 실시간 동기화
3. **무중단 전환**: 기존 사용자 영향 최소화하면서 모듈별 마이그레이션
4. **결제 연동**: Danal 결제 시스템을 Django로 통합

### 1.2 Background

- **Phase 1 완료**: Django API 94% 일치도 달성, 핵심 엔드포인트 구현 완료
- **현황**: PHP 레거시와 Django가 분리된 상태 → 통합 필요
- **목표**: 6개월 내 첫 모듈(채용정보) 완전 전환

### 1.3 Predecessor Phase

- **Phase 1**: 마이그레이션 (Django API 기반 구축) - ✅ 완료
  - 참고 문서: docs/01-plan/features/마이그레이션.plan.md

### 1.4 Successor Phase

- **Phase 3**: 모듈별 완전 전환 (채용정보, Business114 등)
  - 하이브리드 연동이 완전히 검증된 후 시작

## 2. Scope

### 2.1 In Scope

**Phase 2-1 (Month 1-2): Nginx 리버스 프록시 구축**
- [ ] Nginx 리버스 프록시 설정
  - `/api/v1/*` → Django Gunicorn (포트 8000)
  - `/*` → Apache + PHP (포트 80)
  - SSL/TLS 설정 (Let's Encrypt)
- [ ] Gunicorn + Systemd 설정
- [ ] 로드 밸런싱 및 헬스 체크 설정

**Phase 2-2 (Month 3-4): 데이터 동기화 파이프라인**
- [ ] 이벤트 큐 구축 (Celery + Redis)
  - MySQL 트리거 → 이벤트 발행
  - Django Celery 워커가 이벤트 구독 및 처리
- [ ] 데이터 동기화 스크립트
  - 회원 (TBL_MEMB) 양방향 동기화
  - 업체정보 (TBL_SHOP, TBL_KEYWORD) 단방향 동기화 (PHP → Django)
  - 채용정보 (TBL_RECRUIT, TBL_RESUME) 단방향 동기화
- [ ] 동기화 검증 및 모니터링 대시보드

**Phase 2-3 (Month 5-6): 결제 시스템 연동**
- [ ] Danal 결제 API를 Django로 래핑
  - 기존 PHP 결제 로직 Django로 이식
  - 결제 결과 양쪽 DB 동시 기록
- [ ] 환불 처리 자동화
- [ ] 결제 이력 동기화 및 모니터링

### 2.2 Out of Scope

- 프론트엔드 변경 (모바일 m/, 데스크톱 /는 그대로 유지)
- 결제 PG 교체 (Danal 유지)
- 메일 서버 구축 (기존 인프라 사용)
- 전체 PHP 마이그레이션 (Phase 3 이후)

## 5. Risks and Mitigation

| Risk | Impact | Likelihood | Mitigation |
|------|--------|------------|------------|
| 데이터 동기화 지연/누락 | High | Medium | 이중 쓰기 + 정기적 검증 배치 작업 |
| PHP/Django 트랜잭션 불일치 | High | Medium | MySQL 트리거 + Celery 재시도 로직 |
| Nginx 다운으로 서비스 중단 | High | Low | 이중 Nginx (Active-Passive) |
| Danal API 장애 | Medium | Low | 로컬 결제 큐 + 수동 재시도 |
| 성능 저하 (동기화 오버헤드) | Medium | Medium | Redis 캐싱 + Celery 워커 스케일링 |
| 클라이언트 캐시 문제 (API 버전 변경) | Low | Low | API 버전 관리 (/api/v1, /api/v2) |

## 6. Architecture Considerations

### 6.1 System Architecture

```
[Client Browser / Mobile]
    │
    ▼
[Nginx Reverse Proxy (www.dongta.com:443)]
    ├─ /api/v1/* ──────────────────────────► [Gunicorn Worker 1,2,3...]
    │                                            │
    │                                       [Django DRF]
    │                                            │
    │                                       [PostgreSQL]
    │                                            ▲
    │                                            │ (동기화)
    │                                       [Celery Worker + Redis]
    │
    └─ /* ────────────────────────────────► [Apache + PHP 레거시]
                                                 │
                                            [MySQL AWS RDS]
```

### 6.2 Nginx 리버스 프록시 설정

```nginx
upstream django_backend {
    server 127.0.0.1:8000;
    server 127.0.0.1:8001;
    server 127.0.0.1:8002;
    keepalive 32;
}

upstream php_backend {
    server 127.0.0.1:80;
    keepalive 32;
}

server {
    listen 443 ssl http2;
    server_name www.dongta.com;

    ssl_certificate /etc/letsencrypt/live/www.dongta.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/www.dongta.com/privkey.pem;

    # API 라우팅 (Django)
    location /api/v1/ {
        proxy_pass http://django_backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }

    # 나머지 (PHP)
    location / {
        proxy_pass http://php_backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # 헬스 체크
    location /health {
        access_log off;
        return 200 "OK";
    }
}
```

### 6.3 데이터 동기화 아키텍처

```
[MySQL 이벤트 트리거]
    │
    ▼
[이벤트 큐 (Redis)]
    │
    ▼
[Celery Worker (Django)]
    │
    ├─► [데이터 검증]
    ├─► [PostgreSQL 쓰기]
    └─► [검증 실패 시 DLQ (Dead Letter Queue)]

[정기 배치 (매시간)]
    │
    ├─► [불일치 데이터 검사]
    ├─► [Slack 알림]
    └─► [자동 복구 시도]
```

### 6.4 Celery + Redis 설정

**Django settings.py:**
```python
CELERY_BROKER_URL = os.getenv('REDIS_URL')
CELERY_RESULT_BACKEND = os.getenv('REDIS_URL')
CELERY_ACCEPT_CONTENT = ['json']
CELERY_TASK_SERIALIZER = 'json'
CELERY_RESULT_SERIALIZER = 'json'

CELERY_TASK_ROUTES = {
    'apps.sync.tasks.sync_member_data': {'queue': 'sync'},
    'apps.sync.tasks.sync_payment_history': {'queue': 'payment'},
}

CELERY_TASK_MAX_RETRIES = 3
CELERY_TASK_DEFAULT_RETRY_DELAY = 300  # 5분
```

**Docker Compose 추가:**
```yaml
celery:
  image: dongta-django:latest
  command: celery -A config worker -l info -Q sync,payment,default
  environment:
    - REDIS_URL=redis://redis:6379/0
  depends_on:
    - redis
```
