### 3.2 Detailed Differences

#### 3.2.1 Password Reset: confirm 엔드포인트 누락 (Design)

**Design**: `POST /api/v1/auth/password/reset/` 만 정의 (재설정 요청만)
**Implementation**: 요청 + 확인 2단계로 구현
- `POST /api/v1/auth/password/reset/` - 이메일 발송
- `POST /api/v1/auth/password/reset/confirm/` - 토큰+새 비밀번호로 재설정

**평가**: 구현이 더 올바름. 2단계 플로우가 보안 표준. Design 문서 업데이트 필요.

#### 3.2.2 Social Login: HTTP Method 및 URL 변경

**Design**: Provider별 GET 엔드포인트 2개
- `GET /api/v1/auth/social/google/`
- `GET /api/v1/auth/social/naver/`

**Implementation**: 통합 POST 엔드포인트 1개
- `POST /api/v1/auth/social/login/` (body: `{provider, access_token}`)

**평가**: 구현이 더 우수. 통합 엔드포인트가 확장성(Kakao, Apple 추가 시)과 유지보수에 유리.
Design의 GET 방식은 OAuth2 redirect 흐름을 암시하지만, 실제 구현은 클라이언트가 access_token을
획득한 후 서버에 전달하는 방식으로, REST API에 더 적합.

## 12. Recommended Actions

### 12.1 Immediate (P1)

1. **Celery Beat Schedule 등록**: `base.py`에 `CELERY_BEAT_SCHEDULE`로 `cleanup_expired_password_reset_tokens` 추가 (매시간)
2. **.env.example 업데이트**: `FRONTEND_URL` 변수 추가

### 12.2 Short-term (P2)

3. **이메일 열거 방지**: 이메일 존재 여부와 무관하게 동일 응답 반환
4. **Rate Limit 추가**: `PasswordResetRequestView`에 `@ratelimit(key='ip', rate='3/h')` 적용
5. **미사용 패키지 제거**: `django-allauth`, `python-social-auth` requirements에서 제거 (또는 allauth로 전환)
6. **Social Login 성공 테스트**: `unittest.mock.patch`로 Google/Naver API mock 테스트 추가

### 12.3 Design Document Update

7. **S4.2 테이블 업데이트**: Password Reset confirm 엔드포인트 추가
8. **S4.2 Social Login 수정**: GET 2개 -> POST 1개 통합 엔드포인트로 변경
9. **S3.2 PasswordResetToken 모델 추가**: Data Model 섹션에 모델 정의 추가
